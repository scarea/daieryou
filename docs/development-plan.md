## 0. 北极星目标
- 先把服务端从“可玩原型”提升到“可稳态运行”，优先解决 OOM、状态一致性、身份安全。
- 在不破坏现有玩法和交互的前提下，逐步引入 Redis 热状态能力，最终可切主存。

## 3. 当前风险清单（按优先级）
1. **高**：Redis 当前仍不是“主热状态”，多实例一致性仍有限（已支持优先读与恢复，但写路径仍内存主导）。
2. **中**：`RoomRepository` 已有 `maxInMemoryRooms` 上限，但阈值需要结合压测校准。
3. **中**：缺少运行时观测指标，不利于提前发现 OOM 前兆。
4. **中**：前端主包体积偏大，冷启动成本高。
5. **低**：账号体系已切到 Mongo，后续需补充迁移脚本与索引巡检文档。

## 8. 代码审查结论（2026-03-06）
### R1 - Redis 镜像重试缺口（高）
- [x] `RoomRepository` 仅在 `saveRoom/deleteRoom` 抛异常时入重试队列；当返回 `false` 时会被当作成功，可能导致镜像缺口。
- [x] 补齐行为：`save/delete` 返回 `false` 也进入 `pendingMirrorOps`，并补单测覆盖。

### R2 - 网关异常反馈不一致（中）
- [x] `server/app.js` 的消息处理 `catch` 仅服务端打印日志，不给客户端返回标准错误体，前端会等到请求超时才感知失败。
- [ ] 补齐行为：统一返回 `400/500` 错误响应，并附带请求追踪 ID。

### R3 - 入站协议校验不足（中）
- [ ] 对 `route/body/id` 缺少统一 schema 校验，异常负载仍走业务分支后再兜底，影响可观测性与稳定性。
- [ ] 补齐行为：增加统一请求校验层（长度、类型、字段白名单）并记录命中指标。
